What a good browser extension project includes

Extension gigs range from small utilities to extensions connected to your own service. Check that the project states:

  • Features and how users interact with them.
  • Browsers supported.
  • Permissions needed, and why.
  • Data: what is stored, where, and whether anything is sent to a server.
  • Store listing: icons, screenshots, description and privacy details.
  • Publishing through your developer accounts.
  • Source code and support after launch.

Ask whether the extension will use the latest extension format required by each browser. Chrome, for example, has moved to a newer format, and extensions built on old versions may stop working or be removed from the store. Building on the current format from the start avoids a costly rewrite later and makes store review smoother for every browser you support.

How to brief an extension developer

  1. The problem the extension solves, and for whom.
  2. How it works: a button, a popup, changes to specific websites.
  3. Websites it needs to work on.
  4. Connection to your service, if any, with API details.
  5. Browsers to support first.
  6. Design: icon, colors and screenshots.

Review the permission list before development starts. An extension that only needs to work on one website should not ask to read every site a user visits. Narrow permissions pass store review faster and earn more trust.

Test the extension in a fresh browser profile, without your own settings and other extensions. Problems that are invisible on the developer's machine often show up there first.

What drives the price

  • number and complexity of features
  • number of browsers supported
  • connection to your own service or API
  • user accounts, payments or data sync
  • store listing preparation
  • support and updates

Red flags

  • Broad permissions with no explanation.
  • Plans to publish under the developer's store account.
  • Hidden tracking or data collection not in the brief.
  • No source code offered.
  • No plan for store review or rejections.

If the extension connects to a larger product, see our software development guide and API integration guide. For the icon, our icon design guide can help.

Prepare the store listing with the same care as the extension itself. Clear screenshots, a short explanation of what the extension does, and an honest description of the permissions help users trust it enough to install. Store reviewers also read the listing, so an accurate, simple description can speed up approval. Plan who will answer user reviews and support questions after launch, since unanswered problems quickly lower an extension's rating.

Quick pre-order checklist

  • I have described the features and target websites.
  • Permissions are as narrow as possible.
  • The extension will be published under my own accounts.
  • I have an honest privacy policy if user data is involved.
  • I will receive the source code.
