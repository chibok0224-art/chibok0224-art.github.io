What a good dashboard package includes

Check that the offer states:

  • Tool and any licenses needed.
  • Data sources connected.
  • Pages and key metrics included.
  • Filters such as date, region or product.
  • Refresh schedule and sharing setup.
  • Documentation of calculations.
  • Revisions and delivery time.

Ask the developer to check key totals against a number you trust, such as monthly sales from your accounting system. Matching numbers build trust in everything else.

Look at examples of the developer's dashboards and ask what decision each one supports. Good dashboard builders talk about the questions and the people using the report, not only about the tool. That mindset is what turns data into something your team actually reads.

How to brief a dashboard developer

  1. The questions the dashboard must answer.
  2. Who will use it and how often.
  3. Data sources and sample exports.
  4. Key metrics and how you define them.
  5. Tool and sharing needs.
  6. An example or sketch you like.
  7. Deadline.

Define your metrics precisely. Words like active customer or revenue can mean different things in different teams. Writing the definition down avoids dashboards that look right but count the wrong thing.

Start with one page that people will use daily, then add detail. A dashboard that is checked every morning is worth more than a large report nobody opens.

Mobile viewing is worth a moment of thought. Many managers open dashboards on a phone between meetings. If that is how yours will be used, ask for a simple mobile layout with the most important numbers at the top, rather than a wide report that needs constant zooming.

What drives the price

  • number of data sources
  • data cleaning and modeling needed
  • number of pages and metrics
  • automatic refresh and access setup
  • custom calculations
  • documentation and training

Connecting one clean spreadsheet costs much less than combining several systems with messy data and complex calculations.

Red flags

  • Lots of charts but no clear key numbers.
  • Numbers that do not match your source systems.
  • Requests for full admin access to everything.
  • No documentation of calculations.
  • A dashboard that only works on the developer's computer.

Check who can see the dashboard after it is shared. Reports often contain sensitive business data, so limit access to the people who need it.

Tips for a smoother project

After delivery, use the dashboard for a few weeks and note what you still check elsewhere. Those gaps show what to add next. Many developers offer small follow-up changes, and a short second round often makes the difference between a nice report and a daily tool.

Quick pre-order checklist

  • I listed the questions the dashboard must answer.
  • My key metrics are defined in writing.
  • Data access uses limited accounts.
  • Totals will be checked against trusted numbers.
  • Refresh and documentation are included.
