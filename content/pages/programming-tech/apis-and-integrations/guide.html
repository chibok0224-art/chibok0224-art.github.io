What a good integration project includes

Integration gigs range from a single automation to connecting several systems. Check that the project states:

  • Systems to connect, and which data moves in which direction.
  • Trigger and timing: when data syncs, and how often.
  • Method: custom code or a no-code tool.
  • Error handling: logs, alerts and retries.
  • Hosting: where the code runs, and its cost.
  • Security: how keys and data are stored.
  • Documentation and handover.

Check the limits of each tool's API before starting. Some APIs are only available on higher plans, some limit how many requests you can make per hour, and some do not expose the data you need. A good developer checks this first and tells you if the plan needs to change, before any code is written or any fee is spent on work that cannot succeed.

How to brief an integration developer

  1. The manual task you want to replace, step by step.
  2. The tools involved, with plan levels, since some APIs need a paid plan.
  3. Example data: a real order, contact or record.
  4. Rules: what to do with duplicates, missing fields or updates.
  5. Volume: how many records per day or month.
  6. Access: test accounts or sandbox environments if available.

Test with real examples, including awkward ones: a customer with no phone number, an order with a refund, a product with special characters. Integrations usually fail on edge cases, not on the normal record you tested first.

Keep the accounts and hosting for the integration in your name. If the developer hosts it on their own server, the integration stops the day that arrangement ends.

What drives the price

  • number of systems and data types
  • one-way versus two-way sync
  • custom code versus no-code tools
  • volume and speed requirements
  • error handling, monitoring and security
  • documentation and support

Red flags

  • API keys requested by plain message or email.
  • The integration runs on the developer's personal account.
  • No plan for errors or failed syncs.
  • No documentation of what was built.
  • Promises that nothing will ever fail.

Plan for change. The tools you connect will update their APIs over time, and old versions are sometimes switched off. Ask the developer how you will know if a connection breaks, and whether they offer support for updates. A monthly glance at the error log, or an alert sent to your email, is often enough to catch problems early before missing data builds up.

Quick pre-order checklist

  • I have described the task and the data flow.
  • API keys and hosting are in my accounts.
  • Errors will be logged and I will be alerted.
  • The integration will be tested with awkward real examples.
  • I will receive documentation.
