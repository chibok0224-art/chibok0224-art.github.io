What a good scripting job includes

Scripting gigs are usually small and priced by complexity. Check that the job states:

  • The task, with input and expected output.
  • Language and what must be installed to run it.
  • How it runs: manually, on a schedule, or with a simple interface.
  • Error handling and logging.
  • Testing with your real examples.
  • Instructions for running and changing settings.
  • Source code.

Ask for settings, such as folder paths, email addresses or file names, to be kept in a separate configuration file. You can then change them yourself without touching the code or paying for small updates.

How to brief a scripting developer

  1. The manual steps you do today, one by one.
  2. Sample input files and an example of the result you want.
  3. Your computer: Windows, Mac or Linux, and whether you can install software.
  4. How often the task runs.
  5. Unusual cases: empty files, missing values, duplicates.
  6. Access to any tools or accounts involved, through separate credentials.

Record yourself doing the task once, with a screen recording and short narration. It is the quickest way for a developer to understand exactly what you do, including small steps you would forget to write down.

Use copies of real files for testing, with personal or sensitive data removed. Scripts often fail on real-world messiness, such as extra spaces or odd date formats, that clean examples do not show.

Ask for a dry-run mode for scripts that change or move files. In a dry run, the script shows what it would do without actually doing it. It is a simple, reassuring way to check the result before letting the script loose on real files for the first time.

What drives the price

  • number of steps and tools involved
  • amount and messiness of data
  • scheduling and running unattended
  • interface or configuration options
  • error handling and logging
  • support after delivery

Small scripts can be inexpensive, but ask what support is included if your files or tools change. A short support period is worth having for the first weeks of use.

Red flags

  • No testing with your real files.
  • Scripts that only run on the developer's machine.
  • Passwords written directly into the code.
  • Data collection from sites that do not allow it.
  • No instructions for running the script.

Keep a backup of your files before running a new script for the first time. A small bug in an automation that renames, moves or deletes files can affect many files at once.

Quick pre-order checklist

  • I have described the manual steps and sample files.
  • The script will run on my computer or chosen server.
  • Settings are kept in a separate file.
  • Errors are logged clearly.
  • I have backups before the first run.
